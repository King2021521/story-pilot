# Story Pilot 技术架构设计

本文档集基于前置需求分析和桌面端产品设计，描述 Story Pilot 的后端技术方案、工程结构、数据模型、存储模型、知识图谱记忆方案、AI 工作流运行时、主流程、IPC/API、安全测试和演进路线。

## 设计结论

Story Pilot 推荐采用“本地优先的桌面应用 + NestJS TypeScript sidecar 后端 + SQLite/Kuzu 双存储 + AI 工作流运行时”的架构。

核心判断：

- 产品不需要把“Agent 聊天”作为主入口。用户操作对象是作品、章节、人物、设定、伏笔、工作单，而不是一段开放对话。
- AI 能力应被封装为可审计的工作流。每次 AI 生成都产生工作单、上下文包、模型调用记录、草稿产物、记忆候选和用户确认结果。
- 正式作品设定必须有边界。AI 可以提出建议，但不能绕过用户确认直接污染 canon memory。
- 关系数据和知识图谱都需要。SQLite 负责事务、版本、审计和源数据，Kuzu 负责复杂关系查询和图谱记忆检索。
- 桌面端应该默认离线可用。联网只用于模型调用、素材导入、同步和可选云备份。

## 架构原则

1. 工作台是事实源入口  
   用户通过结构化工作台管理创作对象。AI 只作为对象动作和工作流能力出现。

2. 本地数据优先  
   作品、设定、章节、记忆、任务记录默认保存在本地项目空间中。用户可以在没有网络时查看、编辑和组织内容。

3. AI 输出必须可追踪  
   每次模型调用都记录输入摘要、上下文来源、模型、参数、成本、输出、解析结果和应用结果。

4. Canon 需要人工确认  
   正式设定、人物关系、伏笔状态、剧情事实和世界观规则必须经过用户确认或规则化操作才能进入正式记忆。

5. 图谱是投影，不是唯一事实源  
   SQLite 保存事务性源数据和事件日志，Kuzu 根据事件投影出图谱。图谱损坏时可以从源数据重建。

6. 工程上避免过早服务化  
   桌面 MVP 不引入 Postgres、Redis、Temporal、Neo4j 服务端集群。先用嵌入式、本地可运维的组件完成闭环。
